开篇：从“一条时间线”到并行的经历(opening) · 原文 ↗

一句话概括：Letta 推出 conversations API endpoints，同一个 agent 可以同时进行多段对话，但身份和记忆仍然只有一份。

背景是 Letta 对 agent 的定位：它要做的是 stateful agent，更像“digital humans”（原文用语），而不只是一个 LLM，有自我认同和经历，记忆从经历中形成。过去这种 agent 只有一条时间线；现在每段 conversation 都归属于某个具体 agent，在任何一段里形成的记忆都会流向它的所有对话。

代表性场景是让一个 agent 当组织的知识管家（原文“institutional knowledge manager”）：Slack 等渠道里每个 thread 对应一段 conversation，几百个并行运转，都汇入同一份记忆；agent 能跨全部对话检索，把工程讨论、产品会议和客户反馈串起来。

在 ADE 里：从主对话分出旁支Conversations in the ADE · 原文 ↗

在 ADE 中，可以从主对话，也就是 “default” conversation，另开独立的 “side” conversation。对面始终是同一个 agent，所以消息可以跨对话检索，记忆共享。

在 Letta Code 里：多个并发 sessionConcurrent Sessions in Letta Code · 原文 ↗

Letta Code 底层已默认改用 Conversations API endpoints。效果是：对同一个 agent 可以同时开多个 session，彼此的记忆和经历是连通的。

设计取舍：共享还是隔离Designing Agents with Conversations · 原文 ↗

服务大量终端用户时，不必再为每个用户建一个 agent。取舍标准只有一条：希望记忆跨用户 session 积累，就考虑 conversations；需要记忆隔离，仍应分别创建 agent。

导读者注：Letta 的共享是 agent 层面、自动流通的；后面的 Apple 论文则只挑四类信息放进 workspace，再在角色权限控制下共享，两者正好对照。
