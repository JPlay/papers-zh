摘要：先抓住三个结论Abstract · 原文 ↗

问题：靠多轮工具调用生成代码的 agentic LLM 系统，每个 session 都从零开始，上次让工作顺利的领域约束、数据 schema、工具配置和输出偏好，结束后全部丢失。

方案：shared selective persistent memory，即“共享、有选择、持久化”的记忆。只保留四类可复用上下文：任务规格、数据 schema、工具配置、输出约束；session 自己的推理轨迹一律丢弃。保留下来的内容打包成 workspace，可在基于角色的访问控制下转交给其他用户。

摘要中值得先记住三个结论。

  • 成本曲线是非单调的。四个公开数据集上的受控复现里，格式规格只在开头给一次，之后不再提供。无记忆十二次全败，输入约 3.8K token；选择性记忆十二次全中，输入约 3.9K；完整对话历史成功八次，输入约 7.7K。作者的口号是“What is kept matters more than how much is kept”：保留什么，比保留多少更重要。
  • 统计上，两种记忆相对无记忆的差异都通过 Bonferroni 校正后的精确 McNemar 检验，p 分别为 0.0005 和 0.008；两种记忆之间完成率分不出高下（p 等于 0.125），区别在价格。无记忆的失败全是规格未满足，产出物结构本身完好。
  • 系统已在实际平台上部署：agent 从 CSV、SQL、REST、MCP 数据源生成用 git 管理版本的产出物。“零 token 数据刷新”把程序和数据拆开，十二次全部触发、中位 0.08 秒、不调用模型；用统计摘要代替原始数据，token 少 97 到 431 倍。在 24 个企业任务上，选择性记忆完成 23 个，另两种是 19 和 17 个，但样本太小，两两差异都不显著；那里用户会重新说明需求，完整历史多花 9 倍输入也毫无改进。

第一节　引言：无状态为什么是浪费Introduction · 原文 ↗

作者的出发点很朴素：agent 已经很能干，但 session 是无状态的（原文“stateless”）。企业用户反复做结构相似的工作，比如每周用新数据重做仪表盘、按固定格式出报告，每次都要把系统“本该记得”的东西再讲一遍。症结不在 LLM 没有记忆，而在于系统没有机制去“留下有用的、扔掉一次性的”。

把整段对话存下来行不行？作者的答案是能用但不划算：公开数据上它把完成数从零提到八，但输入是紧凑规格的两倍，而后者能十二次全中；企业任务上则多花 9 倍输入、毫无改进。作者猜想旧的工具轨迹可能还会误导模型，但承认实验证明的是成本，不是这个机制。

核心观察是：可复用的知识能拆成四个正交类别，各自紧凑、跨 session 稳定、存下来有益。

  • 任务规格：用户自定义的 system prompt，写领域规则、格式和偏好，例如达成率不低于百分之九十五用绿色。
  • 数据 schema：预先算好的列名、类型、统计摘要和数据源之间的关系。
  • 工具配置：可用工具、参数 schema、调用方式和认证要求。
  • 输出约束：产出物与运行环境之间的契约，例如数据运行时注入、绝不写死。

丢弃的是推理轨迹、工具调用日志、中间文件和出错恢复路径。作者措辞克制：证据说明这些“不值这个价”，并不说明它们有害。

三项贡献：一是这套记忆架构加零 token 刷新机制，见第三节；二是协作式 workspace 平台，有 git 版本化、草稿隔离、多连接器和 AI 辅助的编辑与查询模式，见第四节；三是三个企业场景的部署案例，见第六节。

导读者注：读这篇论文，可以抓住一条主线。作者并不声称模型因此变聪明了，而是论证两件事：一是只保留“对下一次有用的结构化信息”，比保留全部过程更便宜，在需要时也更可靠；二是让程序和数据分离，很多更新根本不用再叫醒模型。后面所有实验，都是围绕这两点展开的。

1.1　三个驱动场景Motivating Use Cases · 原文 ↗

后面的任务都按这三类组织：

  • 周期性刷新：分析师每周重做供应链仪表盘，每次四到五轮、重复交代八到十二条格式约束；有了记忆，约束自动保留，换数据即可零 token 刷新。
  • 跨团队共享：总监把营收 workspace 发布成带版本的模板，同事加载后接上 schema 兼容的自家数据，在权限控制下直接看到结果。
  • 迭代式构建：团队跨多个 session 扩充同一个 workspace，规格一路累积，草稿隔离保护已发布版本，git 回退可恢复任意历史状态而无需调用模型。

四条线归结到同一个区别：别人要么存得太多太粗，要么不跨 session 存配置。

加长上下文窗口只加预算、不决定存什么；RAG 在文档粒度检索，不是结构化配置；对话摘要仍带着推理轨迹；MemGPT 关注对话连续性，Generative Agents 关注叙事连贯，Reflexion 只在单个任务内总结失败。本文则规定四类信息跨 session 保存，并主动丢弃轨迹。

A-MEM 的笔记网络、Mem0 的长期事实库、LangGraph 区分 thread 内 checkpointer 与跨 thread store，都把记忆做成结构化记录，其中 LangGraph 和本文的 session、workspace 划分最接近。差别是它们“学习”该存什么，本文的类别事先固定、与产出物契约绑定，不够通用但能直接落地。相比给每段内容打分的上下文压缩方法，本文的遗忘是粗粒度、声明式的，整类丢弃。

第三节　架构本体Shared Selective Persistent Memory · 原文 ↗

整体流程：用户在对话式前端操作；每个 session 开始时从 workspace 取出选择性记忆；agentic 引擎靠工具调用生成和编辑带版本的产出物，外部数据经多连接器层接入；产出物只能经运行时注入契约读数据；workspace 只记录四类记忆，从不记录轨迹。

3.1　问题形式化Problem Formulation · 原文 ↗

用符号说：查询 q、system prompt s、工具步骤序列 T、产出物 a，现有系统在 session 结束后整体丢掉。用户回来做相关任务时，s 里的领域约束、q 里的 schema 假设、T 里的工具配置、a 里的格式契约都得重新交代。作者认为这既是用户摩擦的主因，也是 token 浪费的主因。

3.2　四类记忆Memory Decomposition · 原文 ↗

  • 任务规格：对基础 prompt 的扩展，由用户编写、多次打磨。例子包括按环节配色，Supply 蓝、Orders 橙、Process 紫；总要有执行摘要卡片；数值运算防 NaN。
  • 数据 schema：列名类型、数值分布、类别取值、行数和样例行，用 pandas 的 describe 加类别分析自动生成。作者特意澄清：画像要读整张表，计算成本随行数增长；有界的只是输出摘要，而且只对行数近似恒定，对列数线性增长，见表三。它让模型不看原始数据也能写对处理代码。
  • 工具配置：工具与连接器、参数 schema、调用方式，如 REST 端点、MCP 服务器、SQL 连接、子 agent 委派，以及认证。企业里这些很稳定，但从头配置很贵。
  • 输出约束：最关键的是数据注入契约，脚本只能从运行时注入点读数据，绝不写死，这是零 token 刷新的前提。

3.3　选择性遗忘Selective Forgetting · 原文 ↗

明确不存六样东西：临时中间文件；用户试过但没保存的改动，撤销栈让试错无风险；推理轨迹；工具调用日志；出错恢复路径；原始数据，由 schema 摘要替代。作者说动机只是“松散地”来自 lost in the middle 研究，但论点关于内容而非位置：旧轨迹可能让 agent 重走老路。

导读者注：此处说“可能误导”，引言和局限部分则强调只证明了“不划算”。两处强弱不一，宜以较克制的表述为准。

3.4　session 开始时的组装Memory Composition at Session Start · 原文 ↗

两个公式，用文字说：system prompt 等于基础 prompt 依次拼上任务规格、工具配置、输出约束，各带小节标题；数据 schema 则附在用户查询后面。组装在应用层完成，模型不知道有持久化机制。

3.5　零 token 数据刷新Zero-Token Data Refresh · 原文 ↗

模型生成的程序在运行时解析、聚合、渲染，连摘要、异常值、排名这类洞察文字也动态计算，所以数据变了无需再调模型。新数据到来时做兼容检查：旧列集合必须是新列集合的子集；兼容就零 token 刷新，否则提示重新生成。因此 schema 只能“加列”，缺列就得重来。

第四节　协作式记忆共享Collaborative Memory Sharing · 原文 ↗

workspace 定义为六元组：四类记忆、最新产出物 a、版本历史 V。它存配置、代码和版本元数据，不存对话、轨迹或日志，作者称之为“a curated artifact store, not a chat history”。

共享分四步：加载，记忆进入同事的 session，草稿隔离保护已发布版本；换数据，接上自己的 SQL、REST 或 CSV，兼容则零 token 渲染；细化，比如“加一张趋势图”，无需重新交代；查询，没有编辑权的人用 AI 查询模式提问。

权限基于 OIDC，三种角色：owner 完全控制；steward 可编辑产出物和任务规格；viewer 可加载、查询、接入自己的数据，但不能改基础 workspace。

第五节　实现Implementation · 原文 ↗

平台由 FastAPI 后端、agentic LLM 引擎、多连接器数据层和对话式前端组成。

Agent 循环Agentic Loop · 原文 ↗

每轮用户输入都新开 session，带上组装好的 prompt 和数据摘要。agent 用 Claude Opus 4，经 Claude Agent SDK 调用文件读写、代码搜索和 shell 等工具，范围限于该用户的工作区。分编辑模式和只读的查询模式。

数据集成Data Integration · 原文 ↗

统一接口把 CSV、SQL、REST，以及走 JSON-RPC 和 mTLS 的 MCP 服务器，规范成表格。不注入原始数据，而是预算统计画像，典型企业表约 500 token，比原始注入少约 100 倍；表越宽画像越大。

持久化与版本管理Persistence and Versioning · 原文 ↗

四类记忆、访问控制列表和数据源配置存在 MongoDB；产出物和版本历史交给 git，支持 diff、分支、回滚。两层都不存对话或轨迹。编辑在隔离草稿中进行，“发布”时才生成新的 git 快照。

保存与回退Save and Revert · 原文 ↗

会话内撤销栈最多十个快照，可退回任意版本且不调用模型；只有明确保存的改动才留下，这本身就是选择性遗忘。

6.2　实验一：记忆条件消融Experiment 1: Memory Condition Ablation · 原文 ↗

24 个周期性任务，三种条件：无记忆，用户完整重新说明；完整历史，注入上次全部记录；选择性记忆，四类记忆加产出物。

评审：两名不参与项目、非作者的业务同事，按渲染正确、数据忠实、格式合规、内容完整四条打分，两人四条全过才算通过，一致性 kappa 为 0.91；盲评，随机顺序，看不到条件、记录和 token 数。但作者指出，只有部分条件带格式规格，评审员可能从格式推测条件。

【表一说明】表一按无记忆、完整历史、选择性的顺序给均值：输入 token 约 2.1K、18.7K、3.4K；输出约 8.2K、9.6K、4.1K；轮数 4.3、3.1、1.4；完成率百分之七十九、百分之七十一、百分之九十六；耗时 285、310、68 秒。也就是说，选择性记忆完成最多、最省，完整历史输入约 9 倍却完成更少。 原文对应位置 ↗

完成数分别是 23、19、17。分场景：周期性刷新 10 个任务中依次完成 10、7、6；跨团队 8 个中依次 8、7、6；迭代构建 6 个中三者都完成 5 个，但选择性记忆把轮数从 6.2 降到 2.8。

重要混杂：选择性一列里，18 个任务走了零 token 刷新、完全没调模型，只有 6 个带记忆调用模型。所以该列 token 和耗时是两条路径的平均，不是单次调用成本；完成率不受影响。逐任务记录没保留，作者只能报告混杂，无法拆分。

显著性：这是配对设计，应用 McNemar 而非 Fisher 检验，但没保留任务级配对，只能在与边际数 23、19、17 相容的所有配对中给范围。最有利时，选择性对无记忆 p 为 0.125，对完整历史 0.031；最不利时分别为 0.219 和 0.070。Bonferroni 校正后门槛为 0.0167，任何配对下都不显著。作者因此只把它当描述性结果：三类场景方向一致，但 24 个任务证明不了。

失败分析：选择性记忆唯一的失败需要跨两个文件 join，而数据 schema 对每个源单独画像、不记录跨源键关系，作者称这是“schema 摘要当记忆”的结构性缺陷。无记忆的 5 次失败全是格式不合规。完整历史的 7 次失败多是照搬旧解法、没回应当前请求，但未按预登记方案标注，只算观察。

6.3　实验二：公开数据集复现Experiment 2: Public Dataset Replication · 原文 ↗

为便于他人复现，换用四个宽度差异很大的公开数据集：World Bank GDP，13,979 行 4 列；UCI Adult Income，32,561 行 15 列；Global Superstore，公开的 1,000 行样本，24 列；NYC 311，5,000 行 44 列。脚注列明来源，并称试验级结果随产出物发布。

先注意：两张表里的“无记忆”不可比。企业实验中用户会重新说明，所以无记忆也有百分之七十九；这里规格在第二阶段被扣下，不带规格就必败。前者测记忆省多少轮，后者测没记忆能否完成。

协议：第一阶段各条件相同，用 V1 数据加完整 prompt 和格式规格生成产出物。第二阶段统一只说“用更新后的数据重新生成”，数据换成 V2，列相同、行打乱、数值扰动正负百分之十五，规格不重复。条件只差在带什么进入第二阶段：什么都不带、第一阶段完整记录含产出物、或任务规格。每个数据集每种条件三次，共 36 次试验、72 次模型调用。完成要求全部校验通过：能渲染、守注入契约、不写死数据、有解析器、列引用正确，外加规格合规，即规格指定了一个任何 prompt 都没出现过的背景色。真正有区分力的只有这最后一条。

【表二说明】表二按无记忆、完整历史、选择性的顺序：完成数和规格合规数都是十二次中的零、八、十二次；输入约 3.8K、7.7K、3.9K；输出约 5.5K、3.5K、4.3K；耗时中位数 130、99、140 秒，因两次试验超过 600 秒而用中位数；工具调用 3.7、3.6、10.1 次。核心对比是：选择性与无记忆输入几乎一样，一个全中、一个全败。 原文对应位置 ↗

分数据集同样整齐：无记忆每个都是三败，选择性每个都三胜，完整历史在一到三次之间。无记忆的产出物八条标准过七条，只差规格。

导读者注：这里的“八条标准”和前面列出的检查项数目对不上。正文列出的是五项结构性检查加一项规格合规，共六项，但这里说八条过七条。原文没有交代另外两条是什么，读者宜知道这一点。

作者提醒，这里检验的是整个 workspace：选择性条件同时带着规格和旧产出物，约束靠哪一个传递分不开；它耗时和工具调用更多，也是因为在改旧产出物而非重写。

更有力的是成本：输入加输出，选择性约 8.2K，无记忆 9.3K，完整历史 11.2K。全中的方案反而比全败的便宜，因为后者花了 5.5K 输出去生成不合格的东西。完整历史能带上规格，但贵一倍、不稳定：4 次失败都是根本没有产出，分布在三个数据集，且记录长度无法预测失败，最短的反而失败。所以作者称之为注入记录后的不稳定，而不是被旧轨迹锚定，后者应表现为产出不合规。

显著性：这次保留了逐次结果，选择性对无记忆 p 为 0.0005，完整历史对无记忆 0.008，都过了 0.0167 的门槛；选择性对完整历史 p 为 0.125，不显著。作者强调，这不是说两者一样：差距是三十三个百分点，在三个数据集上方向一致，只是四个不一致配对不足以确立；按百分之三十三的失败率，每个条件约需 21 次试验。因此“结构化记忆更好”的主张，落在明确的成本差异上。

零 token 刷新单独评估，作者承认此前把它和记忆混在一起，导致原来的表无法解读。在 12 次选择性试验中全部触发，不调模型，中位 0.08 秒。但 V2 按构造保留所有列，兼容检查必然通过，所以这只证明机制能执行，不代表真实更新的兼容比例。另外，表二的 140 秒是受控比较的代价：实验中刷新后还会再生成一次，实际部署则停在 0.08 秒的刷新。

6.4　实验三：token 效率Experiment 3: Token Efficiency · 原文 ↗

比较三种数据表示：原样注入、截断到前 50 行、统计摘要。

【表三说明】表三按规模列出原始、截断、摘要的 token。不到一千行：3.2K、1.8K、0.4K；一千到一万行：28.5K、1.9K、0.5K；超过一万行：142.3K、2.0K、0.6K；企业均值：48.7K、1.9K、0.5K；公开均值：789.1K、4.4K、1.8K。行数跨三个数量级，摘要始终约 0.5K；但 44 列的 NYC 311 摘要要 4.5K。相对原始注入节省 97 倍和 431 倍，相对截断只有 2 到 3 倍。 原文对应位置 ↗

第二版在这里做了更正：初版声称摘要总在 1K token 以内，重跑公开数据后发现这只对行数成立。UCI Adult 有 32,561 行，摘要仅 922 token；按列数 4、15、24、44 排序，摘要为 339、922、1,584、4,486 token，单调上升。1,000 行的 Superstore 摘要比 UCI Adult 还大。原数据集都不超过 15 列，所以之前没测到。结论：摘要让成本与表长脱钩，而表长正是每次刷新会变的维度；但对表宽仍是线性的，宽表会吃紧。

作者认为真正该比的是截断：只省 2 到 3 倍，企业从 1.9K 到 0.5K，公开从 4.4K 到 1.8K，最宽表上只有 2.05 倍。摘要的价值主要在保真：只取前 50 行会丢掉尾部分布和稀有类别，导致 24 个企业任务中 5 个出错。

6.5　实验四：用户研究Experiment 4: User Study · 原文 ↗

十二人，六名工程师、六名分析师，四个顺序平衡的任务。周期性生成快 14 倍，12 秒对 165 秒，走的是零 token 刷新路径；表一的约 4.2 倍是两条路径的平均。细化快 2.5 倍，带约束生成快 3 倍。Likert 各维度都偏向选择性记忆，“愿意再次使用”差距最大，七分制下 6.5 对 4.2。平均每个 session 用回退 1.8 次。

第七节　讨论与结论Discussion and Conclusion · 原文 ↗

两次消融对完整历史的评价看似矛盾：企业任务上 17 对 19、输入 9 倍；公开数据上八对零、显著。作者用一个设计差异解释：企业实验里无记忆条件会重新说明，用 4.3 轮对 1.4 轮，说全了就不需要记忆，所以记忆换来的是轮数而非完成率；公开实验扣下规格，不带就失败。要点是：用户愿意把话说全时，记忆不提升 agent 的能力，只省掉重说。完整历史也能提供上下文，但成本翻倍，十二次里有四次无法解释的失败。作者主张这种拆分适用于任何从结构化数据生成产出物的 workspace。

证据分量上，企业结果过不了多重比较校正，只能促成一次功效足够的复现；公开复现更强。两项效率结果是架构性的：零 token 刷新免去模型调用，用户研究中该路径快 14 倍；摘要式生成在需要调用时省 97 到 431 倍 token。二者都是减少调用次数和成本，而非提升推理。git 版本和回退让用户掌控记忆生命周期。

结论措辞是“suggest”：在企业场景中，提升 agentic LLM 效率的首要杠杆是上下文管理，而不是模型能力。

导读者注：把全文压缩成一句话就是：记忆的价值不在“多”，而在“对”。对比开头的 Letta 文章，Letta 让同一个 agent 的所有对话自动共享经历，Apple 这篇则主张由用户撰写、按类别筛选、可以交给同事复用的 workspace 记忆，并且明确把过程性的轨迹排除在外。两种思路并不冲突，前者更像个人助手的连续记忆，后者更像团队里可审计、可回滚的工作模板。

局限性Limitations · 原文 ↗

架构层面六点：四类拆分靠人工设计，自动识别可复用上下文仍是开放问题；零 token 架构只适用于 schema 稳定的表格数据，流式、非结构化或实时 API 数据需要更强的兼容检查；各连接器的故障如超时、认证过期、schema 漂移各自处理，没有统一重试；评分不涉及美观和信息层次；用户研究仅十二人，不足以对单个 Likert 题做检验；共享只到 workspace 粒度，不能单独分享工具配置之类的组件。

证据层面的局限Evidence · 原文 ↗

  • 每格只跑一次，无重复种子；企业任务的差异都过不了校正。
  • 缺三条基线：摘要化历史、手写说明文件（实践者最可能的对照）、逐项去掉一类记忆的消融。
  • 完整历史有混杂：差在信息内容，也差在写得好不好。
  • 只用一个模型家族，没与 MemGPT、A-MEM、Mem0 或 RAG 正面比较。
  • 公开样本功效不足，十二对八约需每条件 21 次；兼容率百分之百是构造出来的，不是测出来的。
  • 任务和评分标准都出自作者，由第三方出题的复现会更有说服力。

未来工作Future Work · 原文 ↗

首要是补上述评估：功效足够、配对、多次运行，加入摘要化历史和手写说明文件基线，以及四类记忆的逐项消融。架构上三个方向：用针对 session 轨迹的分类器学习该存什么；让近期没被验证的规格逐渐衰减，这是参与者提出的；agent 级记忆，保存有效的工具序列和出错恢复经验。作者强调它与 workspace 记忆性质不同，是学来的、agent 私有的，需要泛化边界、过期检测和与显式规格冲突时的裁决规则。此外还想支持流式和事件驱动的刷新。

伦理考量Ethical Considerations · 原文 ↗

作者声明系统不存储、不处理个人可识别信息：记忆都在 workspace 层面，评估数据都是汇总的运营指标，个性化不涉及个人画像或行为追踪。安全方面，SQL 凭据、REST 的 API token、MCP 的 mTLS 都限定在单个 workspace，不跨 workspace 泄露；文件访问限于用户 session 目录，产出物在沙箱浏览器环境运行。产出物只经注入点拿数据，不持有连接器句柄或凭据，连接器调用由后端按所属 workspace 解析，未挂载的连接器会被拒绝。
